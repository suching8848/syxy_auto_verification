# 断网恢复速度优化方案（评审修订版）

> 初版日期：2026-09-19；实施状态更新：2026-09-23。基准：v1.7.5 源码及 09-15、09-16 本机历史日志。
> 状态：阶段 A 已完成；阶段 B 候选版已在本机试用，快速重试经一晚受限试用后恢复默认关闭；阶段 C 的 `v2.0` 发布包已准备，尚未替换 runtime 或对外发布。以下早期章节保留当时的设计与证据边界，实际进度以 §7、§10 为准。
> 目标：减少工具可控制的认证等待，保持成功判定可靠、请求有界、守护可停止。
> 不承诺“断网后 3 秒必恢复”；服务器是否接受认证和实际网络耗时不由本工具控制。

## 1. 已知证据与未知事项

### 1.1 日志能够证明什么

证据文件：`runtime/CampusNet/logs/auto_login_2026-09-15.log`、`auto_login_2026-09-16.log`。

| 事件 | 09-15 | 09-16 |
|---|---|---|
| DOWN | 18:57:19 | 18:57:36 |
| 第一次失败（登录 POST 耗时） | 18:57:20（69ms） | 18:57:36（68ms） |
| 第二次失败（登录 POST 耗时） | 18:57:24（150ms） | 18:57:41（63ms） |
| 登录接口成功（POST 耗时） | 18:57:31（191ms） | 18:57:47（199ms） |
| RECOVER | 18:57:32 | 18:57:49 |
| 日志记录的恢复时长 | 13s | 13s |

两次均先收到 `mac collision`，随后登录成功并检测到联网恢复。

注意计时口径：

- Auth 日志的毫秒数只覆盖登录 POST 及其响应读取，不包含前面的门户发现、index.jsp、Cookie 获取、参数补全和后面的联网复核。
- 前两次失败后的计划等待为 3 秒和 5 秒，共 8 秒；其余时间不能全部归为退避。
- 当前失败计数达到阈值后会清零，即使已确认断网，下一次认证仍需再次累计检测失败，形成额外调度延迟。
- 首次确认断网还同步执行 `log_failure_context()`，其中 TCP 诊断也可能增加等待。
- 当前 outage_start 在确认 DOWN 时重新赋值；日志的 13 秒不包含实际掉线到首次发现、以及完整的首次确认时间。
- 冷却期间仍持续探测网络，“这几秒网络完全没被使用”的说法不成立。

### 1.2 不能从现有证据得出的结论

- `mac collision` 说明门户报告会话冲突；不能据此确定手机抢占账号、单账号仅允许一台设备或固定的会话清理时长。
- 两次第三次尝试成功，不代表把第三次提前就一定成功；服务端可能尚未准备好。
- 两天都在 18:57 左右发生故障，应同时考虑学校固定时刻事件。程序启动后约 7 分钟不是会话周期的证明。

**09-20 更新（五天样本）**：09-15 ~ 09-18 连续四天，首次 DOWN 分别出现在 18:57:19 / 18:57:36 / 18:57:51 / 18:58:06，都是故障日志中的唯一一次。四天复现是很强的相关性，但**目前无法区分两种解释**：

| 解释 | 说明 |
|---|---|
| 固定墙钟事件 | 学校侧或门户在每天 18:57 前后做会话/ACL 刷新 |
| 启动后固定时长 | 守护每天 18:50 启动，故障在启动后第 7~8 分钟——可能是会话年龄或本地定时机制 |

**两者当前不可区分，因为触发时间被计划任务固定在 18:50**。要分辨需做一次错峰实验：把启动时间提前或推迟约 10 分钟，若故障仍在 18:57，则支持墙钟事件；若跟着变成启动后 7~8 分钟，则应查本地程序、会话年龄或其他定时机制。在此之前**不得**认定是学校侧定时事件。
- `response missing 'baidu'` 是代码对响应不含关键词的通用判断，不能证明 Clash/TUN 加工了内容。
- 先前记录的单次探测计时可供参考，但缺少充分样本和一致的代理条件，不能据此认定探测永远不是瓶颈。

## 2. 首版范围

实施三件事：

1. 对明确识别的会话冲突实行有限快速重试，其余失败保留渐进退避。
2. 分离“首次断网确认”和“已断网后的重试调度”，消除重复确认带来的等待。
3. 补充阶段耗时和分类日志，说明发生了什么、下一次何时重试。

保持现有每日触发时间、守护时长和认证模式。静默路径不增加窗口、托盘或气泡，不主动登出，不采用并发抢登。全天常驻、代理策略和协议续期另行评估，不捆绑进入首版。

## 3. 认证结果与错误分类

### 3.1 用明确结构承载结果

建议引入 `AuthResult`，至少包含：

- `ok`：是否已通过最终联网复核；
- `failure_kind`：`session_conflict`、`credential_error`、`network_error`、`verification_failed`、`unknown`；
- `message`：经过脱敏、限长的原因；
- `timings`：本次认证各阶段耗时；
- `portal_accepted`：门户是否明确返回成功，用于区分登录拒绝与联网复核失败。

门户请求层可以有内部结构，但不得把“门户成功”直接当成 `ok=True`。`do_auth()` 仍以实际联网复核为准。

兼容方案：新增结构化认证入口，原 `do_auth()` 保留布尔包装，检测循环使用新入口；或在一次变更中更新所有 CLI、GUI、托盘调用点和测试。禁止直接把原布尔返回值替换成非空元组：`if (False, message)` 仍为真，会造成认证误报成功。

### 3.2 分类规则

| 类型 | 识别原则 | 策略 |
|---|---|---|
| session_conflict | 已观察到的明确 `mac collision`；以后仅补有样本或协议依据的同义错误 | 有限快速重试 |
| credential_error | 明确错误码或明确“密码错误”等完整措辞 | 常规退避，提示检查账号 |
| network_error | 请求超时、连接错误等 | 常规退避，**不快速重试** |
| portal_config_error | 门户报“设备未注册 / SAM+/portal 参数不一致”一类配置错误 | 常规退避 + 提示用户（见 3.3） |
| verification_failed | 门户已接受，但联网复核仍未通过 | 常规退避，继续网络探测 |
| unknown | 缺少 message、非 JSON、结构异常、未识别拒绝 | 常规退避，记录脱敏诊断 |

不得把“账号”“用户名”“invalid”等泛化子串当作永久错误依据；“账号已在线”不等于账号凭证错误。未知错误不得默认持续快重试。

**`network_error` 明确排除在快速重试之外**：09-19 的样本（门户在 40 秒内连续 3 次拒绝、最终由网络自行恢复）说明，门户不可用期间加大请求频率不会缩短恢复时间，只会把 3 次请求变成几十次。快速重试只对“门户在线但拒绝会话”这一类有效。

### 3.3 portal_config_error：伴随代理环境出现的门户侧拒绝

09-19 的样本提供了一个待验证的机制假设，必须单列一类：

| 时间 | 代理状态 | 探测 | 门户回应 |
|---|---|---|---|
| 09-15 ~ 09-18 | 断网时已关闭 | 稳定（各 6 行超时） | `brac error: create session failed(mac collision)!` |
| 09-19 | **全程开启** | 33 次超时（是前几天的 5 倍以上） | `WEB认证设备未注册，请确认SAM+/portal/设备上的参数配置是否一致` |

**可以确认的**：代理开启时，门户发现阶段失败，程序只拿着 `wlanuserip` 直接调用门户，随后收到“设备未注册”。这说明**代理很可能破坏了门户发现或参数获取**——正常情况下那一步会从重定向 URL 里取到 `wlanacname`/`nasip` 等参数。

**不能确认的**：代理具体**如何**造成这一点。不能断言是“TUN 换掉了来源身份”——那是从现象推到机制，缺少证据。手机登录同一账号只能解释 `mac collision`，解释不了“设备未注册”，但“设备未注册”的确切成因尚未查清。

由此得到的结论：

- 这类拒绝**不会通过重试解决**，快速重试只会放大失败次数；
- 它属于**用户可处置**的问题，提示应写成“**关闭代理/TUN，并检查门户参数配置**”，而不是断言因果；
- 代理开启时**探测本身也失真**（33 次超时）。代理开启期间的 `observed_recovery_ms` 与阶段耗时都不代表校园网的真实情况，样本必须按代理状态分开标注。

因此 §5 的验证清单追加一条：**样本必须记录“本次故障时是否挂着代理”**；代理开启期间的样本不与关闭期间的样本合并统计。


用户提示示例：

> 门户报告会话冲突，可能与旧会话或其他设备有关；将在 N 秒后重试。若其他设备正在使用同一账号，可断开后对照观察。

只在现有 GUI 日志和文件日志中显示，静默守护继续无提示运行。

## 4. 重试状态机与预算

### 4.1 参数先测量，候选策略不视为生产默认值

阶段 A 只增加计时，保持当前重试策略。取得多次可比较的故障样本后，再决定阶段 B 的参数；除 A.2 明示的那一次对照实验外（需用户明确同意、且与守护互斥运行），不为了凑样本主动制造认证冲突。

候选试验配置如下，必须可配置、可关闭，并保留用户现有常规退避设置：

```json
{
    "auth_conflict_retry_seconds": 1,
    "auth_conflict_initial_fast_retries": 5,
    "auth_conflict_later_retry_seconds": 2,
    "auth_conflict_max_fast_retries": 15,
    "auth_conflict_fast_window_seconds": 25
}
```

- 前 5 次额外快速认证，每次从上一次认证完成后等待 1 秒；随后等待 2 秒。
- 首次认证不计入额外次数。最多 15 次额外认证，且只允许在首次明确冲突返回后的 25 秒内发起；两者先到者生效。
- 发起时间必须严格早于窗口截止；恰好到截止点也不再发起快速认证。已在途的请求正常收尾，不再追加请求。
- 忽略请求耗时的理想时间线是 1、2、3、4、5、7、9…23 秒；25 秒的预约已经越界，因此不能写成“必定执行 15 次”。实际请求耗时会进一步减少次数。次数上限仍用于约束配置调整后的行为。
- 两种间隔至少 1 秒，后期不短于前期；次数上限为 0 时禁用快速路径。非法类型、负数和极端值须校验。
- 这些是待比较的起始参数，不是从两次历史故障推导出的最优值。

### 4.2 状态与转换

按一次故障维护：`total_failures`（诊断累计）、`backoff_step`（常规退避级数）、`fast_retries_used`、`fast_window_started_at`、`fast_budget_closed`、`next_auth_at`。诊断计数与调度计数分离，快速失败不能直接把常规退避推到 300 秒。

1. 正常状态累计 `fail_threshold` 次连续失败，进入已断网状态；首次探测失败时间单独保留，不被确认时间覆盖。
2. 已断网后继续探测联网，不再重复累计两次失败才允许认证；仍离线且到达 `next_auth_at` 才认证。
3. 每次认证失败均递增 `total_failures`，不因类型变化丢失诊断记录。
4. 明确冲突且预算尚未关闭时，按前 5 次 1 秒、随后 2 秒预约；实际发起前检查次数和窗口，执行时递增 `fast_retries_used`。
5. 出现其他错误、次数耗尽或时间截止时，单向设置 `fast_budget_closed=True`。本次故障内不再打开快速路径，即使后续错误又变回冲突。
6. 首次转入常规退避时设置 `backoff_step=1`，使用 `auth_retry_delay(config, backoff_step)`。从最近一次失败认证完成时计算截止；如窗口关闭时该截止已经过去，可在下一次调度时立即进入常规尝试，不额外叠加等待。后续每次常规尝试失败才递增 backoff_step。
7. 因此使用当前默认配置时，快速路径结束后的等待为 3、5、10、20…秒，不跳到 40/300 秒。自定义常规配置仍然生效。非冲突错误从第一次失败开始走这套常规退避。
8. 网络确认恢复后才清空全部故障状态和预算。门户 success 但联网复核失败不算恢复；错误类别改变不算恢复。
9. 新一轮独立守护使用全新状态。停止后重新启动会建立新预算，这与同一故障内自动重新获取预算应明确区分。

候选策略示意：

```text
明确冲突 → 有限 1s/2s 快速阶段 → 单向关闭快速预算
        → 常规 backoff_step=1 → 3s → 5s → 10s → 20s …
        → 只有联网确认恢复，才允许下一次故障获得新的快速预算
```

### 4.3 调度和停止

- 使用单调时钟记录间隔；墙上时间只用于日志和每日时间显示。
- 下一次唤醒取当前状态仍有效的“下次探测、认证截止、快速窗口截止、运行结束”中的最近时间。已处理或关闭的截止项必须移除/推进，不能让过去的截止时间造成零等待忙循环。停止/运行结束优先于发起请求，联网恢复优先于认证；快速窗口到期优先于同刻的快速预约。
- 首版保持同步请求，不在已有请求未结束时启动新的请求。1 秒是计划等待，不是整个认证周期上限。
- 停止事件在等待、请求前和每个网络阶段之间检查。已有阻塞 I/O 无法被检查瞬间打断，应在测试和界面说明中保留这个边界。
- `log_failure_context()` 不应阻塞首次认证：优先使用已有诊断信息，额外 TCP 探测移出首次认证关键路径或失败后再做。
- 核查 GUI“立即认证”与自动守护的并发调用；在进程内共用认证锁，避免两路同时提交。锁等待必须可停止。取得锁后重新检查停止/运行结束、快速窗口及联网状态，避免手动认证已恢复网络后，自动守护仍提交过期预约；锁等待单独计时，不算网络耗时。进程间互斥另立事项，不能宣称全机绝无重复认证。

## 5. 可观测性与验收口径

新增单调时钟计时：

| 指标 | 定义 |
|---|---|
| probe_ms | 一次网络检测完整耗时 |
| confirm_ms | 首次失败到确认 DOWN 的时间 |
| portal_discovery_ms | 门户发现、页面和会话参数准备耗时 |
| login_post_ms | 登录 POST 及响应读取耗时 |
| verify_ms | 认证后联网复核耗时 |
| auth_total_ms | 一次认证完整客户端耗时，含失败路径；即所讨论的 auth_cycle_ms，统一命名避免重复 |
| conflict_first_at / conflict_last_at | 本次故障首次与最后一次收到明确冲突的时间 |
| first_portal_success_at | 冲突后首次收到门户成功的时间；没有成功则留空 |
| observed_release_interval | 由末次冲突尝试与首次成功尝试的起止时刻构造的放行观测区间，含请求耗时误差；仅用于 A.2 对照实验与有成功样本的故障 |
| auth_http_request_count | 一次认证实际发出的 HTTP 请求数，含补参请求；辅助评估请求量 || retry_wait_ms | 两次认证间工具安排的等待 |
| retry_lateness_ms | 实际发起认证相对计划截止的延迟 |
| observed_recovery_ms | 首次检测失败到联网恢复的时间 |

完整客户端耗时不是服务端 CPU、数据库或会话创建成本。HTTP 请求数同样只是压力的代理指标，不能证明服务端负载可忽略。

`auth_http_request_count`（实现中的 `http_requests` + `socket_probes`）是**部分计数**：它只统计 `opener.open()` 显式发起的请求，**不含** urllib 自动跟随的重定向、也不含认证后的联网复核请求。它可用于比较同一路径下的相对请求量，**不得**被称为"一次认证的完整请求总数"。若要精确总请求数，需要替换 urllib 的 handler 或从日志侧统计，属阶段 B 范围。

`conflict_last_at - conflict_first_at` 仅表示观察到冲突的跨度，不是冲突真实持续时间，也不能单独给出放行区间。在假定冲突消退后保持稳定、请求条件一致时，可用最后失败尝试与首次成功尝试构造带请求耗时误差的放行区间；若未成功，则是未观察到恢复的样本，不能排除它只统计成功案例。保留每次请求起止时间，不把响应时刻当成精确服务端状态切换时刻。

可以先收集 10 次以上作为初步复盘目标，但样本数量本身不保证代表性。09-15 与 09-16 是不同日期、相似时段的两个样本；同一时段反复出现的故障可能相关。标记日期、网络/代理条件及用户操作，避免仅凭少量同质样本认定最优参数或可靠 P95。

保留既有日志格式兼容 `humanize()`，新字段或新日志行需同步测试。实际网络掉线时间只有在人工标记或独立测量时才可计算，不与 observed_recovery_ms 混称。

日志不得加入密码、完整 POST 表单、Cookie、完整会话令牌或可还原账号的响应字段。用于分享的事件摘要脱敏。可将保留期扩至 30 天并设置轮转/容量上限；不要新增无限增长的 events.log。

### 验收目标

- 确定性模拟中，明确冲突后按 1 秒预约，不额外重复累计 fail_threshold。
- 快速次数与时间上限严格生效，预算耗尽后退避继续增长。
- 模拟“服务端第 2 秒恢复可认证”和“第 12 秒才恢复”两种场景，分别测量；不能假定服务器提前放行。
- 在无阻塞模拟中，调度误差不超过一个实现定义的唤醒粒度；真实网络中将请求耗时与调度等待分别报告。
- 真实校园网按相同配置、代理条件和人为操作记录多个样本；有足够样本后报告中位数、P95、样本量与每次故障认证次数。样本不足只展示逐次记录。
- 若执行 A.2 对照实验，单独记录每次实验的放行观测区间、尝试次数与采样间隔；实验样本与自然故障样本分开统计，不合并成同一组分布。
- **启用快速路径前必须确立前置条件**：`session_conflict` 在真实环境中是否可复现。现有证据为 09-15、09-16 两次故障记录，但两次都发生在同一时段，**不能假定它们统计独立**——它们可能同源，甚至都来自同一次学校侧事件。而同一账号并不保证必然产生 `mac collision`。**后续未再出现该错误，只表示暂未触发，不构成删除该功能的理由。** 若长期没有样本，则不应为了保住该功能而放宽分类规则（例如把泛化拒绝或未识别错误也纳入冲突），按 A.6 的“证据不足时默认关闭”处理即可。
- 需一并检验一个尚未排除的机制：失败认证**自身**是否会在门户留下会话残留，从而使下一次登录更易被拒。若成立，重试策略本身就是冲突的部分成因，参数必须更保守。相关线索见 A.5，**不作因果判定**。
- 不以候选参数直接替换线上值；参数调整须有样本依据（自然样本或对照实验），并保留回退到常规退避的开关。
- 目标是减少可控等待，不以“必须达到 3 秒”替代实际测量。若冲突增多、恢复变慢或请求数超预算，关闭快速路径回退。

## 6. 测试与实施顺序

### 阶段 A：先建立基线

归档仍存在的历史日志，在本地保存脱敏摘要；使用实际运行 exe、配置及计划任务信息记录版本与条件。先增加阶段计时，确认主要延迟分布。

#### A.1 被动采样（默认）

沿用现有部署，不改动手机或代理状态。每次自然发生的冲突记录 `conflict_first_at`、`conflict_last_at`、`first_portal_success_at`、每次尝试的起止时刻与 `auth_total_ms`。样本按日期、时段、网络与代理条件标记。

被动采样的问题：09-15 与 09-16 是不同日期的相似时段，可能相关（同一条 ACL、同一次学校侧事件），不能直接假定为两个独立样本；放行区间只能依靠离散请求结果估计。

#### A.2 可选对照实验（非开工前置条件）

目的：在明确记录操作与环境的条件下，缩小恢复观测区间、比较不同采样策略；仍不能直接测得服务端精确放行时刻或资源成本。

- 默认采用自然故障样本及本地模拟服务器。用户明确选择对照实验后，才手动改变手机或代理条件；手机登录同一账号并不保证制造 mac collision，未出现目标错误就记录“未复现”，不要继续强造冲突。
- 执行真实门户实验前，停止其他守护/手动认证来源，保证只有一个请求发起者；不要让日常任务与实验同时抢登。
- 出现明确冲突后，可在用户选择的实验中每次认证完成后等待 2～3 秒再尝试，记录每次完整认证的起止时间、结果和请求数。这里是认证尝试，不是仅探测门户可达性。
- 同时设定最长 60 秒及最多 15 次额外认证，两者先到者停止；到截止时间不再发新请求。现有阻塞请求可能稍后才返回，不能宣称观察上限等于进程硬退出时限。
- 门户首次成功后做联网复核；成功则结束实验。若门户成功但复核失败，停止额外登录并记录此区别，不能继续用冲突实验代替网络排障。
- 出现其他错误、响应显著变慢或用户要求停止时立即停止发起新请求，记录结果后恢复原运行方式，不主动注销网络。
- 操作可能影响电脑和手机两端上网。实验不是默认流程或计划任务的一部分；只在明确授权后实施。
- 不成功的实验也要保留，记为“观察期内未恢复”；单次实验不能用于推导分布或最佳参数。

#### A.3 实验能回答和不能回答的问题

可比较客户端完整耗时、恢复观测区间及请求次数。响应变慢或新错误是停止实验的信号，但未出现异常并不证明服务器能无成本承受重试；冲突变长也不能仅凭一次实验归因于负载。

若出现压力迹象，应降低重试频率，即增大等待间隔、减少次数或关闭快速路径，而不是缩短间隔。

#### A.4 结束条件

阶段 A 完成后，至少应能回答：一次认证的完整客户端耗时、每次故障的尝试次数、放行时刻的**观测区间**及其采样条件。未恢复的样本记录为未恢复，不要求必须得到成功区间才能开始开发。无需等满 10 次故障才能编写代码。启用策略统一见 A.6。

#### A.5 记录可用于区分的线索字段（不作因果判定）

“门户自身的会话残留”与“本工具重试造成的会话残留”是两种可能机制，需要线索字段来逐步排除，**但不能凭单次尝试的序号直接判定成因**。每次故障额外记录：

| 字段 | 记录目的 |
|---|---|
| 本次故障内的认证序号 | 冲突出现在第几次尝试，用于观察是否存在模式 |
| 每次尝试的返回结果与类别 | 观察冲突是否成串出现、是否只出现在特定顺序 |
| 每次尝试的起止时刻与请求数 | 与 retry_wait_ms 分离，判断间隔是否被压缩 |
| 本次故障开始前是否已有未完成的认证 | 排除重叠提交这一确定性的自身成因 |
| 同账号其他设备当时的登录状态（用户标注） | 提供外部因素线索，但依赖用户配合，可能缺失 |

**为什么不能据此判定**：

- **首次尝试也可能触发服务端状态变化**——第一次请求失败不等于门户此前已有残留；它本身就在建立或改变会话状态。
- **第 2 次之后的冲突也可能来自其他因素**——其他设备抢占、学校侧 ACL 刷新、门户内部超时清理，都可能在同一时间窗内发生，与我们的重试无因果关系。
- 因此“重试越密、残留越多”目前只是**一个未验证的假设**，不能写成结论。

**可承担的结论上限**：这些字段只能给出**相关性线索**。要支持“工具自身制造残留”这一判断，至少需要满足：第 1 次尝试干净（无冲突、无重叠提交）、其他设备状态已知且未登录、冲突在第 2 次之后稳定出现，**并且重复多个独立样本**。**多次出现相同顺序仍只能增强怀疑，不能证明冲突由本工具制造。**

任一条件缺失时，只能记为“机制未确定”。这不等于什么都不能做：

- **可以**为降低请求压力而放慢重试（增大间隔、减少次数、关闭快速路径）——这是基于压力与风险的保守选择，不需要先查明原因；
- **不可以**据此宣称“已查明是工具制造残留”，并以此为依据缩短间隔、增加重试次数或收窄分类规则。

换言之：证据不足时，调整方向只允许**更保守**，不允许**更激进**。

#### A.6 启用策略（统一口径）

本节是“何时可以启用快速路径”的**唯一判定处**，§5 验收目标与 A.4 均以此为准。

| 阶段 | 允许做的事 | 门槛 |
|---|---|---|
| 开发 | 编写 `AuthResult`、分类、状态机、退避衔接 | 无门槛，随时可开始 |
| 模拟验证 | 用假时钟与模拟响应验证时序与预算 | 离线测试全绿 |
| 真实启用 | 在真实门户上开启快速路径 | **需审阅基线**；证据不足时**默认关闭** |

- **证据不足的两种处理**：默认关闭快速路径（保留分类日志与退避衔接修正照常生效），或明确标注为**受限试用**并记录观察期。二者择一，不得含糊过去。
- **不因“长期未复现冲突”而删除该功能**：未复现只表示尚未触发，功能可保留在关闭状态。
- **不得为保住功能而放宽分类规则**：把泛化拒绝、未识别错误纳入 `session_conflict` 是不可接受的替代方案。
- 关闭快速路径后，§4.2 的 `backoff_step` 衔接与 §3 的分类日志仍然独立成立——**即使快速路径永不启用，这两部分也值得保留**。

### 阶段 B：实现核心优化

实现结果结构、明确分类、有限快速重试与截止调度。保留门户 success + 联网成功双重判定，保持 CLI 的成功/失败退出码语义。

回归至少覆盖：

1. 明确冲突、密码错误、含“账号”的冲突描述、未知拒绝、缺字段、非 JSON、HTTP/连接错误。
2. 首次确认阈值不变；已断网后不重复确认；恢复后重置截止时间和预算。
3. 次数耗尽、窗口耗尽、恰好到截止点、请求跨越窗口、不同错误混合；确认快速阶段退出后从常规第一级起步且不能重新开启预算；持续失败最终到达上限。
4. 恢复后再次断网获得新预算；界面停止后不发起下一次认证。
5. 门户成功但复核失败；网络自行恢复时取消待执行重试。
6. GUI 手动认证与守护同时触发时不重叠；CLI、http/browser 模式返回语义不变。
7. 新配置缺失、非法配置与旧配置兼容；日志脱敏及 humanize 兼容。

使用假时钟和模拟响应验证时序，不以真实 sleep 构造脆弱测试，也不连接真实门户验证错误密码。

- 全量离线测试通过后构建新版本，校验内嵌版本、源码和 exe 一致。
- 先备份本机实际 exe 和配置，再替换运行副本；保持每日时刻和时长不变。
- 带完整测试配置的静默冒烟确认无窗口、正常结束及联网日志；缺账号场景退出码 1 才正确。退出码 0 本身不能证明发生过成功认证。

## 8. 延后单独评估的项目


### 8.1 全天值守

每天 30 分钟是当前用户选择的使用窗口，不自动视为缺陷。全天常驻会改变流量、日志、启动身份及凭据查找行为，需独立选择。

若采用开机任务，必须先核对所用 exe 支持的参数、SYSTEM/用户会话区别、APPDATA 归属、代理环境及浏览器模式兼容性，不能只把触发器改成 AtStartup 就宣称可用。不得与既有每日任务重叠运行。重复触发的接缝与 IgnoreNew 行为需要验证，没有固定“30 秒接缝”的依据。

### 8.2 代理与探测地址

保留能反映互联网是否可用的外部探测；校园内可达地址只能辅助判断门户可达，不能作为已联网依据。响应关键词、重定向检查仍保留。

若测试显式绕过应用代理，需对比系统代理启停及 TUN 情况；应用层禁用代理不保证绕过 TUN 路由。探测与认证路径应一致、可解释，不能仅凭 missing keyword 判断代理有问题。

### 8.3 续期与硬超时

当前每几秒已做连通性检测，新增每 5～6 分钟探测不是主动保活。只有找到门户支持的续期接口、协议依据和可验证会话行为后，才另做续期设计。

`time.monotonic()` 只能计时，不能中断阻塞的 urlopen/read。总截止方案必须说明 DNS、连接、重定向、分块读取的剩余预算，以及取消后资源回收；不能用后台线程超时后仍继续提交认证的办法制造更多重叠请求。

## 9. 配置、任务和发布事实澄清

- 当前本机日常入口为 runtime/CampusNet/CampusNet.exe；通常读取同目录配置，目录不可写时还有 APPDATA 回退。以运行记录为准，不绝对写成“只认 exe 旁边”。
- 根目录配置用于源码调试，和 runtime 独立是便携部署设计，不需要为了合并而引入目录联接。目录联接不能直接指向单个 JSON 文件。

- packaging/make_release_zip.py 的 copy2 只复制白名单文件，包括示例配置，不包含真实凭据。archive 里的真实配置来自旧部署目录归档，不是发布脚本泄漏。
- .gitignore 只能防止通常的误提交，不能防止手动分享整个目录。不得将含配置的 runtime/archive 目录作为发布内容。
- 日志清理按 mtime 和保留期执行。09-15、09-16 日志不会仅因到了 09-19 就超过 7 天；应及时保全所需证据，但不能用错误日期制造紧迫性。
